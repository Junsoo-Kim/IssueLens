# RAG 파이프라인 설계문서

IssueLens 장애 진단 챗봇의 데이터, 청킹, 색인, 검색, 생성 설계와 각 설정값을 정한 이유, 값을 바꿨을 때의 차이를 정리한다. 전체 기획은 [기획서](IssueLens_기획서.md), 증빙은 [체크리스트](evidence_checklist.md)를 따른다.

> 청킹 비교(증빙 05)와 5.4절(증빙 06)의 수치는 로컬 증빙 `data/processed/evidence/05_chunk_count_compare.txt`, `06_topk_compare.txt`(2026-10-22 실행)에서 옮겼다. 증빙 파일은 원문 일부가 들어 있어 레포에 없다.

## 1. 전체 흐름

```text
[수집]  GitHub REST API: 얕은 수집 7,319건 -> 태깅·선별 -> 상세 수집(댓글, 타임라인, 연결 PR)
[정제]  Markdown 정제, 비밀정보 마스킹, 봇·자동 안내 댓글 제외, 해결 근거 판정(strong/medium/weak)
[분리]  최종 색인 580건 / 평가용 160건 / 예비 25건  (평가용은 색인·질문 시점 수집 모두에서 제외)
[색인]  RAG 1 issue_metadata: 이슈 1건 = 레코드 1개 (580)
        RAG 2 issue_documents: 이슈 본문·댓글·PR 설명·PR 변경 내용 3,725문서 -> 청크 10,520개
        각각 Chroma(Dense) + BM25(Sparse), 같은 결정적 ID
[검색]  질의 분석 -> 저장소 라우팅 -> RAG 1 Hybrid(RRF) 상위 이슈 -> 그 이슈로 범위를 좁힌 RAG 2 Hybrid -> 근거 선별
[그래프] LangGraph retrieve: 최대 3회 시도(원래 질문 -> 영어 재작성 검색어 -> 질문 시점 수집 후), 시도마다 근거 판정
         LangGraph generate: 근거만 사용한 답변, 인용 번호 검증, 근거 부족 시 답변 거부
```

## 3. 청킹

| 문서 유형 | chunk_size | chunk_overlap | 이유 |
|---|---:|---:|---|
| 이슈 본문 | 900 | 150 | 이슈 템플릿의 한 섹션(환경, 재현 절차, 로그)과 짧은 로그 블록이 한 청크에 들어가는 크기. 겹침 약 17%로 섹션 제목과 앞 문맥이 경계에서 끊기지 않게 함 |
| 댓글 | 700 | 100 | 댓글은 대부분 짧아 댓글 1개가 1청크(평균 1.7). 긴 댓글만 나눠 해결 설명이 다른 댓글과 섞이지 않게 함 |
| PR 설명 | 800 | 120 | 무엇을·왜 바꿨는지가 한 청크에 남는 크기 |
| PR 변경 내용 | 1,200 | 0 | 파일 경로와 hunk 단위로 자른다. hunk끼리는 독립적이라 겹침을 두면 같은 코드 줄이 중복 근거로 나온다 |
| 공식 문서 | 1,000 | 150 | 섹션 단위 (현재 색인에는 공식 문서 본문이 없음, 링크만 기록) |

- 모든 청크 앞에 `[저장소#번호] 이슈 제목 / 컴포넌트 / 문서 유형` 머리말을 붙여 임베딩과 BM25 입력에 넣는다. 짧은 댓글 청크도 어떤 이슈의 무슨 문서인지 검색에 반영된다.
- Markdown 구조와 코드 블록을 우선 경계로 나누고(`RecursiveCharacterTextSplitter`), 긴 코드 블록만 2차로 나눈다.
- 설정은 `configs/retrieval.yaml`의 `chunking`에서 바꾼다. 같은 설정으로 다시 색인하면 청크 ID와 개수가 그대로다(F2002, 증빙 02).

### 값을 바꿨을 때 (증빙 05, F2005)

모든 유형의 chunk_size와 chunk_overlap을 절반으로 줄여 같은 3,725문서를 다시 나눴다 (색인은 바꾸지 않고 계산만).

| 설정 | 청크 수 |
|---|---:|
| 현재 (본문 900/150, 댓글 700/100, PR 800/120, patch 1,200/0) | 10,520 |
| 절반 (본문 450/75, 댓글 350/50, PR 400/60, patch 600/0) | 19,465 (약 1.85배) |

청크가 작아지면 개수가 늘어 임베딩 비용과 색인 크기가 커지고, 한 청크에 로그와 그 설명이 함께 들어가지 못해 근거 하나만으로 원인을 읽기 어려워진다. 반대로 지금보다 크게 하면 한 청크에 서로 다른 섹션이 섞여 Dense 검색의 의미가 흐려지고, 근거 8건을 프롬프트에 넣을 때 길이 상한(근거당 1,200자)에 걸려 뒷부분이 잘린다.

## 4. 색인

| 항목 | 값 | 이유 |
|---|---|---|
| Dense | OpenAI `text-embedding-3-small`, 1,536차원, cosine | 한국어 질문과 영어 이슈의 교차 검색 기준선. LangChain·Chroma 연동이 단순함 |
| Sparse | `rank_bm25` BM25Okapi, 저장소별 인덱스 | 예외명, 버전, 설정 키, 클래스 경로처럼 정확히 일치해야 하는 토큰에 강함. 기술 토큰(점·밑줄·숫자 포함)을 지우지 않는 전용 토크나이저 |
| 저장소 | Chroma `issue_metadata`, `issue_documents` 분리 | 이슈 단위 검색과 문서 단위 검색의 단위가 달라서 |
| ID | `issue:{owner}:{repo}:{번호}`, `doc:{문서 ID}:{청크 번호}` | 결정적 ID와 content hash로 upsert해 재색인해도 늘지 않고, 바뀐 레코드만 다시 임베딩 |

## 5. 검색

### 5.1 질의 분석과 라우팅

- 질의 유형: `error_log`(예외명·스택 트레이스·로그 레벨), `natural_language`, `condition_search`, `selected_issue`
- 정확 토큰: 예외명, 버전, 설정 키, 패키지 경로, 상태 코드. 한국어 조사가 붙어도(`NotFoundException이`) 뽑는다
- 라우팅: 사용자가 고른 저장소 → 선택 이슈의 저장소 → 질문에 명시된 저장소 → RAG 1 검색 결과의 저장소 분포로 1~2개

### 5.2 Hybrid 검색과 RRF

```text
RRF(d) = w_sparse / (k + rank_sparse(d)) + w_dense / (k + rank_dense(d)),  k = 60
```

| 질의 유형 | Sparse | Dense | 이유 |
|---|---:|---:|---|
| 오류 로그 | 0.60 | 0.40 | 예외명·로그 문구의 정확 일치가 더 중요 |
| 자연어 | 0.40 | 0.60 | 표현이 다른 증상 설명, 한영 교차 검색 |
| 조건 탐색 | 0.50 | 0.50 | 조건(토큰)과 증상(의미)이 함께 중요 |
| 선택 이슈 후속 | 0.40 | 0.60 | 후속 질문은 자연어가 대부분 |

점수 범위가 다른 BM25와 cosine을 정규화하지 않고 순위로만 합쳐, 한쪽 점수 분포가 결합을 독점하지 않게 한다. k=60은 RRF의 일반적인 기본값으로, 상위 몇 개 순위 차이를 과하게 키우지 않는다.

### 5.3 Top-k

| 단계 | 설정 | 값 | 이유 |
|---|---|---:|---|
| RAG 1 이슈 | `sparse_top_k`, `dense_top_k` | 30, 30 | 두 검색이 서로 놓친 이슈를 RRF에서 보완할 만큼 넓게 |
| | `fused_top_k` | 30 | 라우팅 판단과 조건 탐색 후보에 사용 |
| | `rerank_top_k` (근거 검색 대상 이슈 수) | 8 | RAG 2 검색 범위. 관련 이슈 몇 건과 비교 사례를 함께 보되 무관한 저장소 댓글이 섞이지 않게 제한 |
| RAG 2 문서 | `sparse_top_k`, `dense_top_k`, `fused_top_k` | 40, 40, 30 | 이슈 8건의 문서(이슈당 평균 6문서, 청크 약 18개) 대부분을 후보로 둠 |
| 최종 근거 | `final_evidence_limit` | 8 | 근거당 최대 1,200자 × 8 ≈ 1만 자로 프롬프트 길이와 비용을 제한하면서 원인·해결·환경 비교에 충분한 수 |
| 다양성 | 이슈당 최대, 문서 유형당 최대 | 3, 4 | 한 이슈나 한 유형(예: patch)이 근거를 독점하지 않게 함 |
| 해결 근거 예약 | 상위 이슈 수 | 3 | 상위 3개 이슈의 병합 PR·유지보수자 댓글을 근거 후보에 우선 넣음 |

선택 이슈 대화에서는 선택 이슈의 메타데이터와 본문을 점수와 무관하게 근거에 넣는다. 거의 같은 내용의 청크(앞 200자 기준)는 하나만 남긴다.

### 5.4 값을 바꿨을 때 (증빙 06, F2006)

같은 질문("DataHub 인덱스 복원 중 NullPointerException이 발생해")으로 근거 검색 대상 이슈 수와 근거 상한을 바꿨다.

| 이슈 Top-k / 근거 상한 | 근거 수 | 근거 이슈 |
|---|---:|---|
| 8 / 8 (기본) | 7 | `datahub#10354` 3건(댓글, 본문 2), `datahub#13067` 4건(본문 2, PR 설명 2) |
| 3 / 4 | 4 | `datahub#10354` 2건(댓글, 본문), `datahub#13067` 2건(PR 설명, 유지보수자 댓글) |

기본값은 같은 이슈의 본문 청크와 PR 설명을 여러 개 담아 원인과 수정 내용을 함께 보여 준다. 3 / 4는 이슈별로 대표 문서만 남아 짧지만, 이슈 본문 하나와 PR 설명 하나가 빠진다. 근거 상한이 줄어도 해결 근거 예약 덕분에 유지보수자 댓글은 남았다.

Top-k를 줄이면 프롬프트가 짧아져 빠르고 싸지만, 근거가 상위 이슈 몇 건에 몰려 환경 비교와 상충 사례를 보여 주기 어렵고, 근거 판정에서 "부족"이 나와 재시도나 질문 시점 수집으로 넘어가는 경우가 늘어난다. 늘리면 관련성이 낮은 근거가 섞여 근거 판정과 답변이 흐려지고 생성 시간이 길어진다.

### 5.5 근거 판정

1. 규칙: 근거 0건이거나, 질문의 정확 토큰이 어느 근거에도 없으면 LLM 없이 부족 (모든 시도를 원래 질문의 토큰으로 판정)
2. LLM: 근거만으로 질문에 의미 있는 답이 가능한지, 관련 근거 번호와 함께 판정. 다른 제품의 근거는 같은 라이브러리·같은 오류일 때만 관련 있다고 봄
3. 부족하면 다음 시도: ① 원래 질문 → ② 프롬프트 1의 영어 검색어 → ③ 질문 시점 수집 후 재검색

### 5.6 질문 시점 수집 (F2003·F2004, NF2002)

- 프롬프트 1이 만든 검색어로 GitHub 종료 이슈를 검색한다. 정확 토큰(예외가 난 클래스 우선, 흔한 예외는 뒤로)을 토큰별 검색어로 먼저 쓴다
- 평가용 이슈는 후보에서 제외하고, 이미 색인된 이슈는 다시 수집하지 않고 검색 범위에만 넣는다
- 프롬프트 2가 제목·요약으로 최대 3건을 고르고, 고른 이슈만 상세 수집해 색인한다 (선택·탈락과 이유를 기록)
- 검색어마다 결과를 캐시해 같은 검색어는 GitHub를 다시 호출하지 않는다 (증빙 04)

## 6. 생성

| 항목 | 값 | 이유 |
|---|---|---|
| 모델 | `gpt-5-mini` | 근거 판정·답변 생성은 `reasoning_effort: low`, 검색어 추출·후보 선별·조건 추출은 `minimal`. 기본 추론량으로는 질문당 1분이 넘어 형식이 정해진 단계부터 낮춤 (평균 약 67초 → 27초) |
| 근거 길이 | 근거당 1,200자 | 최종 근거 8건 기준 프롬프트 길이 제한 |
| 출력 형식 | 요약 / 원인 후보 / 환경 비교 / 확인 절차 / 근거 부족 또는 주의사항 | 원인과 확인 절차를 분리하고, 근거끼리 충돌하거나 해결이 확인되지 않은 부분을 숨기지 않게 함 |
| 인용 | 주요 주장마다 `[근거 N]` | 없는 번호를 인용하면 한 번 다시 생성하고, 그래도 남으면 지우고 경고 (증빙 08) |
| 답변 거부 | "제공된 문서에서 확인되지 않습니다." | 세 번 시도 후에도 근거가 부족하거나, 답변 단계에서 근거가 질문과 맞지 않는다고 판단한 경우 (증빙 09). 일반 지식 답변은 사용자가 켠 경우에만 "RAG 미사용" 섹션으로 분리 |

## 7. 검증

- `pytest`: 가짜 LLM·임베딩·GitHub 응답으로 수집, 색인, 검색, 그래프, 화면을 테스트
- `scripts/run_eval.py`: 검증 질문 세트 17개 (근거 있음, 오류 로그, 근거 없음, 조건 탐색, 선택 이슈 후속). 수치 점수 대신 기대 결과와의 일치만 확인
- `scripts/export_evidence.py`: 요구사항 정의서 4장 명령 출력 증빙

### 확인된 한계

- 로그만으로 제품을 알 수 없는 경우(로거 이름이 줄어 있는 로그 등) 다른 제품의 비슷한 이슈를 근거로 답할 수 있다. 로그 진단 화면에서 저장소를 고르면 해결된다 (검증 질문 q07·q17)
- 색인 이슈에 원인·해결 설명이 없으면 관련 이슈가 있어도 답하지 않는다 (q05). 지어내지 않는 쪽을 택했다
- 근거 판정이 "충분"이어도 답변 단계에서 근거가 맞지 않는다고 보면 답하지 않으며, 이때는 질문 시점 수집까지 다시 가지 않는다
